## หลักการออกแบบสี่ข้อ

1. **สิทธิ์ทั้งหมดบังคับที่ฐานข้อมูล** — `anon key` อยู่ในโค้ดหน้าเว็บที่ใครก็อ่านได้ การซ่อนปุ่มบนหน้าจอไม่ใช่การควบคุมสิทธิ์ ทุกตารางใน `public` เปิด RLS และการกระทำที่อ่อนไหวทำผ่าน RPC ที่ตรวจบทบาทเอง ตาราง `role_menu_permissions` ควบคุมแค่การแสดงเมนู
2. **เลขบัญชีธนาคารอยู่นอกขอบเขต API** — schema `private` ไม่ถูก expose จึงไม่มี endpoint ให้ยิงถึง ทุกการเข้าถึงผ่าน RPC ที่บันทึก audit พร้อมวัตถุประสงค์ บทบาทอื่นเห็นเพียงจุดสีเขียว
3. **เอกสารที่จ่ายเงินแล้วเปลี่ยนไม่ได้** — บังคับด้วย trigger ไม่ใช่ข้อตกลงระหว่างผู้ใช้ และร่องรอยการใช้งานลบไม่ได้แม้โดยผู้ดูแลระบบ
4. **เอกสารแต่ละฉบับต้องผ่านมือมากกว่าหนึ่งคน** — ผู้ตรวจสอบต้องไม่ใช่ผู้จัดทำ บังคับที่ฐานข้อมูล เปิด/ปิดได้ตามอัตรากำลัง และการปิดถูกบันทึกไว้
5. **คอลัมน์ที่เป็นผลคำนวณและหลักฐานว่าใครทำ หน้าเว็บเขียนไม่ได้** — ยอดเงิน เลขที่ใบสำคัญ สถานะ และผู้จัดทำ ถูกถอนสิทธิ์ `UPDATE` ออกจาก `authenticated` เพราะ RLS กั้นได้ทีละแถวแต่กั้นทีละคอลัมน์ไม่ได้ ค่าเหล่านี้มาจาก trigger และ RPC เท่านั้น
6. **อัตราค่าตอบแทนมาจากหลักเกณฑ์ ไม่ใช่ความจำของผู้กรอก** — ตาราง `pay_rates` เติมอัตราและคำนวณเงินให้ และปฏิเสธการกรอกที่เกินเพดานหรือผิดจากอัตราตายตัว

## ข้อควรระวัง

`service_role` key ของ Supabase **ห้ามอยู่ใน repo นี้ ในไฟล์ `.env` หรือใน environment ของ Vercel ฝั่ง client**
key นี้ข้าม RLS ได้ทั้งหมด ถ้าหลุดเท่ากับเปิดฐานข้อมูลทั้งระบบรวมถึงเลขบัญชีธนาคาร

**repo นี้เป็นสาธารณะ** (เพื่อใช้ GitHub Pages ฟรี เหมือนระบบ AAMS) จึงห้ามมีไฟล์ข้อมูลหรือเอกสารภายในอยู่ในนี้
`.gitignore` กัน `*.pdf`, `*.csv`, `*.xlsx`, `*.docx`, `TCMS-BCNB.md` และ `_private/` ไว้แล้ว
และ `deploy.yml` ตรวจซ้ำก่อน deploy ทุกครั้ง — ไฟล์ที่ commit ไปแล้วจะอยู่ในประวัติ git ตลอดไปแม้ลบภายหลัง

ควรเปิด secret scanning และ push protection ของ GitHub ไว้ด้วย

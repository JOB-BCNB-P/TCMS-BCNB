# TCMS-BCNB — รายงานความเสี่ยงและมาตรการควบคุม

จัดทำก่อนเริ่มพัฒนา frontend เพื่อให้แก้ที่แบบ ไม่ใช่แก้ที่โค้ดภายหลัง
ระดับความรุนแรง: **สูง** = ทำให้ข้อมูลรั่วหรือเงินผิดได้ทันที · **กลาง** = ทำให้ตรวจสอบไม่ได้หรือทำงานผิดพลาด · **ต่ำ** = คุณภาพและความยั่งยืน

---

## ก. ความเสี่ยงที่จัดการแล้วในรอบนี้

### 1. บัญชีนอกโดเมนเข้าระบบได้ — สูง

Supabase ไม่ได้บังคับ `hd` claim ของ Google Workspace ให้อัตโนมัติ การตั้งค่าเฉพาะฝั่ง Google Cloud Console อย่างเดียว ยังมีช่องให้บัญชี Gmail ทั่วไปสมัครเข้ามาได้ในบางการตั้งค่า

**มาตรการ** — trigger `enforce_bcn_domain` บน `auth.users` ปฏิเสธที่ชั้นฐานข้อมูล บวกกับ `is_active = false` เป็นค่าตั้งต้น ผู้ใช้ใหม่จึงเห็นข้อมูล 0 แถวจนกว่าผู้ดูแลระบบจะอนุมัติ

### 2. ผู้ใช้ยกระดับสิทธิ์ตนเอง — สูง

`raw_user_meta_data` ของ Supabase **ผู้ใช้แก้ไขเองได้** ผ่าน `supabase.auth.updateUser()` ระบบใดที่อ่านบทบาทจากที่นั่นเท่ากับให้ผู้ใช้ตั้งบทบาทตัวเองเป็น admin ได้

**มาตรการ** — บทบาทเก็บใน `public.user_profiles.role_id` เท่านั้น คอลัมน์นี้ถูก `REVOKE UPDATE` จาก `authenticated` และแก้ได้ผ่าน RPC `admin_set_user_role` ซึ่งตรวจบทบาทผู้เรียกก่อน พร้อมกันไม่ให้ผู้ดูแลระบบลดสิทธิ์บัญชีตนเอง (กันล็อกตัวเองออกจากระบบ)

### 3. anon key เปิดเผยต่อสาธารณะ — สูง

`VITE_SUPABASE_ANON_KEY` อยู่ใน JavaScript bundle ใครก็เปิดดูได้ ความปลอดภัยทั้งหมดจึงอยู่ที่ RLS ตารางใดที่ลืมเปิด RLS = ข้อมูลสาธารณะ

**มาตรการ** — migration `0005_rls.sql` วนเปิด RLS ทุกตารางใน `public` แบบอัตโนมัติ ตารางที่เพิ่มใหม่ในอนาคตต้องเปิดด้วยมือ **ให้ตรวจ Security Advisor ของ Supabase ทุกครั้งหลัง deploy**

### 4. เลขที่บัญชีธนาคารรั่ว — สูง

ข้อมูลนี้รั่วแล้วกู้คืนไม่ได้ และเป็นข้อมูลส่วนบุคคลตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล

**มาตรการ** — เก็บใน schema `private` ซึ่ง **ไม่ถูก expose ผ่าน Data API** จึงไม่มี endpoint ให้ยิงถึงเลย เข้าถึงได้เฉพาะผ่าน RPC ที่ตรวจบทบาท บังคับระบุวัตถุประสงค์ และบันทึก `audit.sensitive_access_log` ทุกครั้ง ส่วนบทบาทอื่นเห็นเพียง `has_bank_account` เป็นจุดสีเขียว ซึ่งเป็นคอลัมน์ที่ trigger ดูแลและ client เขียนไม่ได้

**ข้อควรระวังในการเขียน frontend** — อย่านำผลลัพธ์จาก `get_bank_account` ไปเก็บใน state ที่ใช้ร่วมกันหรือใน cache ของ TanStack Query ให้ดึงตอนกดดูเท่านั้น และล้างเมื่อปิด modal มิฉะนั้นเลขบัญชีจะค้างอยู่ในหน่วยความจำของเบราว์เซอร์และอาจถูกดึงออกมาทาง React DevTools

### 5. แก้ไขเอกสารที่จ่ายเงินไปแล้ว — สูง

ข้อผิดพลาดชนิดที่หน่วยตรวจสอบจับได้ทันทีและอธิบายไม่ได้

**มาตรการ** — trigger `guard_voucher_header` และ `guard_voucher_mutable` ปฏิเสธการแก้ไขและลบทุกกรณีเมื่อสถานะ `paid` เอกสารสถานะ `verified` แก้ได้เฉพาะผู้ดูแลระบบ RLS ยังจำกัดซ้ำอีกชั้นหนึ่ง (แก้ได้เฉพาะ `draft`/`submitted`) — ป้องกันสองชั้นโดยตั้งใจ

### 6. เจ้าหน้าที่การเงินแก้ยอดเงินได้ — สูง

RLS ของ PostgreSQL ทำงานระดับแถว ไม่ใช่ระดับคอลัมน์ ถ้าให้สิทธิ์ `UPDATE` แก่การเงินเพื่อให้เปลี่ยนสถานะได้ จะแก้ `total_amount` ได้ด้วย

**มาตรการ** — การเงินไม่มีสิทธิ์ `UPDATE` บน `payment_vouchers` เลย การเปลี่ยนสถานะทั้งหมดผ่าน RPC `set_voucher_status` ซึ่งเป็น state machine ที่ระบุชัดว่าใครเปลี่ยนสถานะใดไปสถานะใดได้ และไม่แตะตัวเลขเงินเลย

### 7. เบิกเกินวงเงินที่จัดสรร — สูง

**มาตรการ** — trigger `guard_budget_ceiling` รวมยอดที่ใช้ไปแล้วของ (รายวิชา × หมวดเงิน) เทียบกับ `course_budget_allocations` ก่อน insert/update ทุกครั้ง ปฏิเสธถ้าเกิน และปฏิเสธถ้ายังไม่ได้ตั้งวงเงิน การตรวจอยู่ที่ฐานข้อมูล ไม่ใช่ที่หน้าจอ จึงหลบด้วยการยิง API ตรงไม่ได้

### 8. เบิกซ้ำใบสำคัญเดียวกัน — กลาง

**มาตรการ** — `treasury_cover_sheet_items` มี `UNIQUE (voucher_id)` ทั่วทั้งตาราง และ `next_voucher_no` ใช้ตารางนับแยก จึงไม่นำเลขที่ที่เคยออกแล้วกลับมาใช้ซ้ำแม้เอกสารถูกยกเลิก

### 9. ร่องรอยการใช้งานถูกลบ — กลาง

**มาตรการ** — `audit.activity_log` และ `audit.sensitive_access_log` มี trigger ปฏิเสธ UPDATE/DELETE ทุกกรณี บทบาท `admin` ของแอปก็ลบไม่ได้ อ่านได้ผ่าน RPC `read_audit_log` เท่านั้น และ schema `audit` ไม่ถูก expose ผ่าน API

### 10. การถอนสิทธิ์ไม่มีผลทันที — กลาง

ถ้าเก็บบทบาทใน JWT (อายุ ~1 ชม.) การถอนสิทธิ์ผู้ใช้จะยังไม่มีผลจนกว่า token จะหมดอายุ

**มาตรการ** — อ่านบทบาทจากตารางจริงผ่านฟังก์ชัน `STABLE` ที่เรียกในรูปแบบ `(select ...)` เพื่อให้ PostgreSQL แคชเป็น InitPlan ครั้งเดียวต่อ query ได้ความถูกต้องทันทีโดยไม่เสียประสิทธิภาพรายแถว
**เพิ่มเติมที่ควรทำ** — ลดอายุ JWT ใน Dashboard เหลือ 30 นาที และเปิด refresh token rotation

## ข. ความเสี่ยงที่ยังเหลือ — ต้องตัดสินใจ

### 11. เลขบัญชีเก็บเป็นข้อความธรรมดาในฐานข้อมูล — สูง · **ตัดสินใจแล้ว: ยอมรับความเสี่ยง + เข้ารหัสไฟล์สำรอง**

ผู้ถือ `service_role` key หรือผู้ที่เข้าถึง Dashboard ของ Supabase ได้ จะอ่านเลขบัญชีได้โดยไม่ผ่าน audit

**สิ่งที่วิทยาลัยเลือก** — ไม่เข้ารหัสในฐานข้อมูล (ไม่ใช้ Vault) แต่เข้ารหัสไฟล์สำรองด้วย AES-256 แทน

**สิ่งที่การตัดสินใจนี้ปิดได้และปิดไม่ได้ — ต้องเข้าใจให้ตรงกัน**

| ช่องทางที่อาจรั่ว | ปิดได้แล้วหรือยัง |
|---|---|
| ยิง REST ตรงไปที่ตาราง | ปิดสนิท — schema `private` ไม่ถูก expose |
| ผู้ใช้ที่ไม่ใช่ admin/finance | ปิดสนิท — RPC ตรวจบทบาทและบันทึก audit |
| ไฟล์สำรองถูกขโมยหรือ Drive รั่ว | **ปิดแล้วด้วยการตัดสินใจนี้** |
| ผู้ถือ `service_role` key | **ยังเปิดอยู่** |
| ผู้เข้าถึง Supabase Dashboard ได้ | **ยังเปิดอยู่** |

สองช่องที่ยังเปิดอยู่จึงต้องคุมด้วยมาตรการเชิงบริหารแทน และควรบันทึกไว้ในเอกสารควบคุมภายในว่าเป็นความเสี่ยงที่ยอมรับไว้โดยรู้ตัว

- จำกัดผู้ถือ `service_role` key ให้เหลือน้อยที่สุด เก็บในที่เก็บรหัสผ่านขององค์กร ไม่ใช่ไฟล์ข้อความ
- จำกัดผู้มีสิทธิ์เข้า Supabase Dashboard และทบทวนรายชื่อทุกภาคการศึกษา
- หมุนเวียน key ทันทีเมื่อผู้รับผิดชอบเปลี่ยน
- ถ้าจำนวนอาจารย์พิเศษเพิ่มขึ้นมาก หรือมีเหตุการณ์ด้านความปลอดภัยเกิดขึ้น ให้ทบทวนการใช้ Vault อีกครั้ง

**ข้อแลกเปลี่ยนใหม่ที่เกิดจากการตัดสินใจนี้** — เมื่อการเข้ารหัสไฟล์สำรองกลายเป็นมาตรการป้องกันชั้นเดียวของไฟล์ที่ออกนอกระบบ **รหัสผ่านของไฟล์สำรองจึงมีค่าเท่ากับข้อมูลทั้งฐาน** ถ้ารหัสผ่านหายก็กู้ข้อมูลไม่ได้เลย ถ้ารหัสผ่านรั่วก็เท่ากับไม่ได้เข้ารหัส วิธีเก็บและการส่งมอบรหัสผ่านอยู่ใน `ops/BACKUP.md` §1 และต้องทำให้ครบก่อนนำข้อมูลจริงขึ้นระบบ

### 12. แผนสำรองข้อมูลและกู้คืน — สูง · **ตัดสินใจแล้ว: pg_dump จากเครื่องของวิทยาลัยเข้า Google Drive**

GitHub ใช้เก็บเฉพาะโค้ดหน้าเว็บ ฐานข้อมูลอยู่ที่ Supabase การสำรองข้อมูลจึงไม่ผ่าน GitHub Actions
(ซึ่งถูกต้อง เพราะการรัน `pg_dump` บน GitHub ต้องเก็บรหัสผ่านฐานข้อมูลไว้ใน GitHub Secrets และ
ไฟล์สำรองที่มีเลขบัญชีจะวิ่งผ่านเครื่องของบุคคลที่สาม)

สคริปต์และขั้นตอนอยู่ที่ `ops/backup-tcms.ps1` และ `ops/BACKUP.md`
ประเด็นสำคัญที่ยังต้องจัดการ

- **ใช้ Shared Drive ของวิทยาลัย ไม่ใช่ Google Drive ส่วนตัวของผู้ดูแลระบบ** — ถ้าผูกกับบัญชีบุคคล วันที่คนนั้นลาออกหรือบัญชีถูกปิด ไฟล์สำรองทั้งหมดหายไปพร้อมกัน วิทยาลัยต้องเป็นเจ้าของไฟล์
- **ยังไม่มี PITR** — ถ้าข้อมูลเสียหายตอนบ่าย จะกู้ได้แค่ถึงรอบสำรองของคืนก่อน งานทั้งวันหายไป ถ้าวิทยาลัยรับความเสี่ยงนี้ไม่ได้ ต้องอัปเกรดเป็นแพ็กเกจ Pro
- **ต้องมีการแจ้งเตือนเมื่อสำรองข้อมูลล้มเหลว** — การสำรองที่ล้มเหลวเงียบ ๆ อันตรายกว่าการไม่มีการสำรองเลย เพราะทุกคนคิดว่ามีอยู่
- **ต้องซ้อมกู้คืนปีละครั้งและบันทึกผลไว้** — ดูรายการตรวจใน `ops/BACKUP.md` §4.2
- ไฟล์สำรองอยู่บนคลาวด์ต่างประเทศ ควรปรึกษาผู้รับผิดชอบด้าน PDPA ของวิทยาลัยก่อนนำข้อมูลจริงขึ้นระบบ

### 13. การแบ่งแยกหน้าที่ — กลาง · **ตัดสินใจแล้ว: บังคับ maker-checker ที่ฐานข้อมูล**

วิทยาลัยเลือกคงบทบาท `admin` ไว้บทบาทเดียว แต่บังคับที่ฐานข้อมูลว่าเอกสารแต่ละฉบับต้องผ่านมือมากกว่าหนึ่งคน
(migration `0007_maker_checker.sql`)

ข้อสังเกตที่เคยพิจารณา: การแยกสองตำแหน่งแต่ใช้อีเมลเดียวกัน **ทำได้ในทางเทคนิคแต่ไม่นับเป็นการแบ่งแยกหน้าที่**
เพราะร่องรอยใน audit จะบอกได้แค่ว่า "บัญชีนี้ทำ" ไม่ได้บอกว่าใครทำ ผู้ตรวจสอบจึงยันไม่ได้ว่ามีคนสองคนจริง
แนวทางที่เลือกจึงคุมที่ **คนละคน** ซึ่งพิสูจน์ได้จาก `audit.activity_log` ไม่ใช่ **คนละบทบาท**

สองสวิตช์ใน `app_settings` แยกกันโดยตั้งใจ เพราะมีต้นทุนต่างกันมาก

| สวิตช์ | ค่าตั้งต้น | เหตุผล |
|---|---|---|
| `control.enforce_maker_checker` (ผู้ตรวจสอบ ≠ ผู้จัดทำ) | **เปิด** | แทบไม่มีต้นทุน ผู้จัดทำคือเลขานุการ/วิชาการ ผู้ตรวจสอบคือการเงิน เป็นคนละคนตามกระบวนงานปกติอยู่แล้ว |
| `control.enforce_checker_payer` (ผู้จ่ายเงิน ≠ ผู้ตรวจสอบ) | **ปิด** | ถ้างานการเงินมีเจ้าหน้าที่คนเดียว จะทำงานไม่ได้เลย ให้เปิดเมื่อมีเจ้าหน้าที่การเงินตั้งแต่ 2 คนขึ้นไป |

การปิดสวิตช์ถูกบันทึกลง `audit.activity_log` และมุมมอง `v_voucher_control_trail`
จะทำเครื่องหมายเอกสารที่ทำในช่วงที่ปิดสวิตช์ไว้ ให้ผู้ตรวจสอบเห็นได้ทันที

**สิ่งที่ต้องทำต่อ** — บันทึกในเอกสารควบคุมภายในว่าวิทยาลัยใช้การควบคุมระดับบุคคลแทนการแยกบทบาท
พร้อมเหตุผลด้านอัตรากำลัง และกำหนดให้สอบทานรายงาน `v_voucher_control_trail` อย่างน้อยภาคการศึกษาละครั้ง

### 14. ชุดทดสอบความปลอดภัย — กลาง · **ทำแล้ว**

RLS policy เขียนผิดหนึ่งบรรทัดเท่ากับข้อมูลรั่วทั้งตาราง และผิดแบบที่มองไม่เห็นจากหน้าจอ

`supabase/tests/rls_smoke_test.sql` มีการทดสอบ 41 ข้อ ครอบคลุมทุกข้อที่เคยระบุไว้ รวมถึง

- เลขานุการแต่ละคนอ่านข้ามสาขาวิชาไม่ได้
- อาจารย์สร้างเอกสารไม่ได้ · ผู้ใช้ที่ยังไม่อนุมัติอ่านได้ 0 แถว
- บทบาทที่ไม่ใช่ admin/finance เรียกดูเลขบัญชีไม่ได้ · การเข้าถึงถูกบันทึก audit
- แม้แต่ผู้ดูแลระบบก็ query ตาราง `private` ตรง ๆ ไม่ได้
- การเงินแก้ยอดเงินไม่ได้ · เอกสารที่จ่ายแล้วแก้และลบไม่ได้ · audit log ลบไม่ได้
- การบังคับวงเงิน · เช็คลิสต์ไม่ครบส่งไม่ได้ · maker-checker ทั้งสองสวิตช์

### 14.2 อัตราค่าตอบแทนเบิกผิด — กลาง · **จัดการแล้ว**

อัตราต่างกันตามแหล่งเงิน ประเภทรายการ และสถานะข้าราชการของผู้สอน (400/800/200/150/100/900)
ถ้าให้ผู้กรอกจำเอง จะเบิกผิดอัตราโดยไม่มีใครจับได้จนถึงชั้นตรวจสอบ

**มาตรการ** — ตาราง `pay_rates` เก็บอัตราตามหลักเกณฑ์ของวิทยาลัย พร้อมช่วงเวลาที่ใช้บังคับ
trigger `guard_pay_rate` เติมอัตราให้อัตโนมัติ คำนวณจำนวนเงินให้ และปฏิเสธเมื่อ

- กรอกอัตราเกินเพดาน (รายการที่หลักเกณฑ์เขียนว่า "ไม่เกิน")
- กรอกอัตราต่างจากที่กำหนด (รายการที่เป็นอัตราตายตัว)
- จำนวนเงินไม่ตรงกับ จำนวนหน่วย × อัตรา
- เลือกรายการที่ไม่ตรงกับหมวดเงิน หรือหมวดเงินที่หลักเกณฑ์ไม่ได้ให้เบิกรายการนั้น

**ที่ต้องตามต่อ** — หลักเกณฑ์ที่ได้รับยังไม่ระบุอัตราค่าตอบแทนผู้ป่วยเสมือน
ระบบตั้งเป็น "เบิกตามจ่ายจริง" ไว้ก่อนเพื่อไม่ให้บล็อกงาน **ซึ่งแปลว่ารายการนี้ยังไม่มีเพดานคุม**
ต้องขอหลักเกณฑ์ฉบับที่ระบุอัตราแล้วใส่เพดานเข้าไป

### 14.3 สองช่องโหว่ที่ชุดทดสอบจับได้ระหว่างทำหน้าข้อมูลหลัก — สูง · **แก้แล้ว**

ทั้งสองข้อคือเหตุผลที่ชุดทดสอบมีอยู่ ไม่ใช่พิธีกรรม — มองจากหน้าจอไม่เห็นทั้งคู่

**ข้อแรก: `FOR ALL` ครอบ SELECT ไปด้วย**

policy `payees_write` เดิมประกาศเป็น `FOR ALL` ซึ่งครอบคำสั่ง SELECT ด้วย
และ PostgreSQL นำ policy แบบ permissive หลายตัวมา **OR** กัน
ผลคือเลขานุการอ่านรายชื่อผู้รับเงินได้ **ทั้งตาราง** ผ่าน `payees_write`
ทั้งที่ `payees_read` ตั้งใจจำกัดไว้เฉพาะสาขาที่ตนดูแล — การกั้นข้ามสาขาบนตารางนี้ไม่เคยทำงานเลย

*แก้แล้ว:* แยกเป็น `payees_insert` / `payees_update` / `payees_delete` ไม่ให้มี policy ใดครอบ SELECT
นอกจาก `payees_read` และเพิ่มด่านในแบบตรวจสุขภาพว่าตาราง `payees` ต้องไม่มี policy แบบ `FOR ALL`

**ข้อสอง: subquery ใน policy ก็ถูก RLS บังคับ ทำให้ `NOT EXISTS` กลับความหมาย**

เงื่อนไข "ผู้รับเงินที่ยังไม่ผูกสาขาวิชา" เขียนตรง ๆ ว่า
`not exists (select 1 from payee_departments where payee_id = payees.id)`
ดูถูกต้อง แต่ subquery นั้นถูก policy ของ `payee_departments` บังคับอีกชั้นหนึ่ง
เลขานุการจึงมองไม่เห็นแถวเชื่อมของสาขาอื่น subquery คืนศูนย์แถว
แล้ว `NOT EXISTS` กลายเป็นจริง → **เห็นผู้รับเงินของสาขาอื่นได้ทั้งหมด**

เงื่อนไขที่ตั้งใจให้แคบลง กลับเปิดกว้างกว่าเดิม และอ่านโค้ดเฉย ๆ ไม่มีทางเห็น

*แก้แล้ว:* ย้ายการตรวจไปไว้ในฟังก์ชัน `SECURITY DEFINER` ซึ่งอ่านตารางเชื่อมได้ครบโดยไม่ผ่าน RLS

**กฎที่ต้องจำสำหรับ policy ที่จะเขียนต่อจากนี้**

1. ใช้ `FOR ALL` เฉพาะเมื่อผู้ที่เขียนได้ ควรอ่านได้ทุกแถวเช่นกัน มิฉะนั้นให้แยกเป็นคำสั่ง
2. `NOT EXISTS` บนตารางที่เปิด RLS ให้ถือว่าผิดไว้ก่อน จนกว่าจะห่อด้วย `SECURITY DEFINER`
3. ทุกครั้งที่เพิ่มการกั้นข้ามสาขา ต้องมีเคสทดสอบ **ฝั่งที่ต้องมองไม่เห็น** ด้วยเสมอ
   ไม่ใช่ทดสอบแค่ว่าฝั่งที่ควรเห็นนั้นเห็นได้

### 14.4 เลขบัญชีค้างในหน่วยความจำเบราว์เซอร์ — กลาง · **จัดการแล้ว**

**มาตรการในหน้าเว็บ** — ช่องเลขบัญชีเรียก RPC ตรง ไม่ผ่าน cache ของ TanStack Query
ล้างค่าออกจาก state ทันทีเมื่อปิดฟอร์มหรือเปลี่ยนหน้า ซ่อนอัตโนมัติใน 45 วินาที
และ **ไม่มีเลขบัญชีอยู่ในไฟล์ส่งออก CSV ของหน้าใดเลย** (ส่งออกได้เท่ากับหลุดได้)
บทบาทอื่นไม่มีแม้แต่ปุ่มให้กด เห็นเพียงจุดสีเขียวว่ามีข้อมูลแล้วหรือยัง

### 14.5 หน้าจอเปิดค้างเมื่อไม่มีคนอยู่ที่เครื่อง — กลาง · **จัดการแล้ว**

Supabase เปิด Inactivity timeout ให้เฉพาะแพ็กเกจ Pro จึงทำที่ฝั่งแอปแทน
ไม่มีการใช้งาน 30 นาที → เตือนล่วงหน้า 1 นาที → ออกจากระบบและล้าง cache ทั้งหมด

**ข้อจำกัดที่ต้องเข้าใจ** — นี่เป็นการป้องกันที่เบราว์เซอร์ ไม่ใช่ที่เซิร์ฟเวอร์
access token ที่ออกไปแล้วยังใช้ได้จนหมดอายุตามที่ตั้งไว้ใน Supabase
มาตรการนี้กันคนที่มานั่งต่อที่เครื่องเดียวกัน **ไม่ได้กันคนที่ขโมย token ไป**

### 14.6 สามช่องโหว่ที่พบระหว่างทำหน้าสร้างเอกสาร — สูง · **แก้แล้ว**

ทั้งสามข้อเป็นชนิดเดียวกัน: **RLS กั้นได้ทีละแถว แต่กั้นทีละคอลัมน์ไม่ได้**
ตาราง `payees` / `clinical_sites` / `user_profiles` ถูกคุมด้วย `GRANT` ระดับคอลัมน์ไว้แล้ว
แต่ตารางเอกสารยังไม่ได้คุม

**ข้อแรก: หน้าเว็บเขียน `payment_vouchers.total_amount` ได้เอง**

ยอดรวมคำนวณด้วย trigger เมื่อบรรทัดเปลี่ยน แต่คอลัมน์นั้นยังเปิดให้ `authenticated` เขียน
ผู้มีสิทธิ์แก้เอกสารของสาขาตน จึงยิง `PATCH` ตรงไปที่ REST เพื่อเขียนยอดใหม่
แล้วส่งเอกสารได้ทันที เพราะการส่งเอกสารไม่ได้คำนวณยอดซ้ำ
**ยอดที่พิมพ์ลงแบบ FM2.2-03 และขึ้นฎีกาจึงไม่ตรงกับผลรวมบรรทัด** และชุดทดสอบเดิมจับไม่ได้
เพราะทุกเคสบันทึกผ่านบรรทัดเสมอ คอลัมน์ `voucher_no`, `status`, `submitted_by`,
`verified_by`, `paid_by`, `payment_date` ก็เปิดอยู่ด้วยเช่นกัน — เท่ากับข้าม
`set_voucher_status` ที่เป็นด่านเดียวของการเปลี่ยนสถานะไปได้เลย

*แก้แล้ว (migration 0014):* `revoke update on payment_vouchers from authenticated`
แล้วให้สิทธิ์เฉพาะคอลัมน์ข้อความบนแบบฟอร์มและช่องลงนาม ยอดเงิน เลขที่ใบสำคัญ
สถานะ และผู้จัดทำ แก้ได้ผ่าน trigger และ RPC เท่านั้น (เทสต์ 52–55)

**ข้อสอง: หน้าเว็บอ้างได้ว่าใครเป็นผู้จัดทำ**

`sync_voucher_keys` เดิมเขียนว่า `coalesce(new.created_by, auth.uid())`
ซึ่งให้ค่าที่หน้าเว็บส่งมา **ชนะ** ผู้ใช้จึงใส่ชื่อคนอื่นเป็นผู้จัดทำ
แล้วไปกด "ตรวจสอบแล้ว" เอกสารนั้นเองได้ โดย `guard_segregation_of_duties` ไม่จับ
การแบ่งแยกหน้าที่ที่บังคับไว้ที่ฐานข้อมูลจึงถูกข้ามได้จากหน้าเว็บ

*แก้แล้ว:* สลับเป็น `coalesce(auth.uid(), new.created_by)` — ผู้ใช้จริงชนะเสมอ
ยังเปิดช่องให้สคริปต์ฝั่งเซิร์ฟเวอร์ (ที่ `auth.uid()` เป็น null) ระบุผู้จัดทำได้ตามเดิม
ใช้กฎเดียวกันกับผู้จัดทำหน้างบฯ และผู้ติ๊กเช็คลิสต์ (เทสต์ 51, 56)

**ข้อสาม: การแบ่งแยกหน้าที่ของหน้างบฯ ไม่ทำงานเลยตั้งแต่ต้น**

`guard_cover_sheet_segregation` ใน migration 0007 ตรวจว่า
`ผู้จัดทำหน้างบฯ = ผู้จัดทำใบสำคัญ` หรือไม่ แต่ **ไม่มีใครเติม
`treasury_cover_sheets.created_by`** ถ้าหน้าเว็บไม่ส่งมาก็เป็น null
เงื่อนไข `v_owner is not null` จึงเป็นเท็จ และ guard ผ่านตลอดโดยไม่ตรวจอะไร
เทสต์ 21 ผ่านมาได้เพราะตัวเทสต์เองส่ง `created_by` มาด้วย

นี่คือการควบคุมที่ "มีอยู่ในโค้ด" แต่ไม่มีผลในการใช้งานจริง ซึ่งอันตรายกว่าไม่มีเลย
เพราะรายงานการควบคุมภายในจะระบุว่ามี

*แก้แล้ว (migration 0013):* เพิ่ม trigger `sync_cover_sheet_keys` เติมผู้จัดทำ
เพิ่ม trigger คำนวณยอดรวมหน้างบฯ จากรายการ ถอนสิทธิ์เขียน `total_amount`
และเพิ่ม `guard_cover_sheet_item` กันการนำใบสำคัญที่ยังเป็นร่าง ถูกยกเลิก ถูกลบ
อยู่คนละปีงบประมาณ หรือยอดไม่ตรงกับใบสำคัญ ขึ้นฎีกา (เทสต์ 44–50)
พร้อมเพิ่มด่านในแบบตรวจสุขภาพว่า trigger ทั้งสามต้องมีอยู่ และต้องไม่มีหน้างบฯ ที่ผู้จัดทำเป็น null

**กฎที่เพิ่มจากรอบนี้**

4. ทุกคอลัมน์ที่เป็น "ผลคำนวณ" หรือ "หลักฐานว่าใครทำ" ต้องถอนสิทธิ์ `UPDATE`
   จาก `authenticated` แล้วให้สิทธิ์กลับเฉพาะคอลัมน์ที่ผู้ใช้กรอกจริง
5. `coalesce(ค่าที่ client ส่งมา, auth.uid())` ผิดเสมอ ต้องเป็น `coalesce(auth.uid(), ...)`
6. guard ที่พึ่งคอลัมน์ใด ต้องมีเทสต์ที่ **ไม่ส่งคอลัมน์นั้นมาจากหน้าเว็บ**
   มิฉะนั้นจะไม่รู้ว่า guard นั้นทำงานหรือผ่านเพราะค่าเป็น null

### 14.7 สองข้อที่โค้ดกับ RLS ขัดกันเอง — กลาง · **แก้แล้ว**

พบจากการรีวิวหน้าจอที่เพิ่งทำ ไม่ใช่จากชุดทดสอบ เพราะทั้งสองข้อ "ไม่ error"

**ข้อแรก: ผู้ดูแลระบบแก้เอกสารที่ตรวจสอบแล้วไม่ได้ และหน้าจอบอกว่าบันทึกสำเร็จ**

trigger `guard_voucher_mutable` และ `guard_voucher_header` เขียนไว้ว่าเอกสารสถานะ
`verified` "แก้ได้เฉพาะผู้ดูแลระบบ" แต่ policy `voucher_update` จำกัดไว้เฉพาะ
`draft`/`submitted` โดยไม่มีข้อยกเว้น ข้อยกเว้นใน trigger จึงไปไม่ถึงเลย

ที่ร้ายกว่าคืออาการ: `UPDATE` ที่ RLS กรองแถวออกทั้งหมด **ไม่ใช่ error**
PostgREST ตอบ 204 หน้าเว็บจึงขึ้น "บันทึกเรียบร้อย" ทั้งที่ฐานข้อมูลไม่เปลี่ยนอะไร
ผู้ใช้เชื่อว่าแก้แล้วและปิดหน้าไป ซึ่งอันตรายกว่าการขึ้นข้อความปฏิเสธ

*แก้แล้ว (migration 0016):* เพิ่ม policy ให้ผู้ดูแลระบบแก้เอกสาร `verified` ได้จริง
ตามที่ trigger ตั้งใจ (เอกสารที่จ่ายเงินแล้วยังห้ามแก้ทุกกรณี — เทสต์ 61)
และฝั่งหน้าเว็บเพิ่ม `assertAffected()` ต่อท้ายทุก `update`/`delete`
ถ้าไม่มีแถวถูกกระทบ จะขึ้นข้อความว่าสิทธิ์ไม่ครอบคลุมเอกสารนี้ในสถานะปัจจุบัน
ไม่ขึ้นว่าสำเร็จ (เทสต์ 58–60)

**ข้อสอง: เจ้าหน้าที่งานการเงินเปิดหน้าหน้างบฯ ได้แต่ไม่มีปุ่มให้กด**

policy `cover_write` ให้สิทธิ์ `('admin','finance')` ทำหน้างบฯ
แต่ `role_menu_permissions` ให้งานการเงินแค่ `can_view` สิทธิ์จริงกับสิทธิ์เมนูไม่ตรงกัน
ผลคือบทบาทที่ฐานข้อมูลออกแบบให้เป็นผู้จัดทำ กลับทำอะไรไม่ได้จากหน้าจอ

*แก้แล้ว (migration 0016):* ปรับสิทธิ์เมนูให้ตรงกับ RLS และเพิ่มด่านทดสอบเทียบสองฝั่ง (เทสต์ 62)

**กฎที่เพิ่ม**

7. `update`/`delete` ทุกจุดต้องต่อ `.select()` แล้วตรวจว่ามีแถวกลับมา
   ไม่มีแถว = ไม่สำเร็จ ห้ามรายงานว่าสำเร็จ

### 15. CSV injection ตอน export — กลาง

ค่าที่ขึ้นต้นด้วย `=`, `+`, `-`, `@`, tab หรือ CR เมื่อเปิดใน Excel จะถูกตีความเป็นสูตร เป็นช่องทางโจมตีเครื่องเจ้าหน้าที่การเงินผ่านข้อมูลที่กรอกเข้ามาในระบบ

**มาตรการที่ต้องทำใน frontend** — ใส่ `'` นำหน้าค่าที่ขึ้นต้นด้วยอักขระเหล่านั้นก่อนเขียนไฟล์ และกรองอักขระควบคุมตอน import

### 16. การนำเข้า CSV จำนวนมาก — ต่ำ

ไม่มีการจำกัดขนาดไฟล์ในข้อกำหนด อาจทำให้เบราว์เซอร์ค้างหรือยิง insert หลายพันครั้ง

**มาตรการที่ต้องทำใน frontend** — จำกัด 2 MB / 1,000 แถวต่อครั้ง แสดงพรีวิวพร้อมทำเครื่องหมายแถวที่ผิดก่อนยืนยัน และแบ่ง insert เป็นก้อนละ 200 แถว

### 17. ความเข้าใจผิดเรื่องเมนูกับสิทธิ์จริง — กลาง

ผู้ดูแลระบบอาจเข้าใจว่าติ๊กเปิดเมนูให้บทบาทหนึ่งแล้วบทบาทนั้นจะทำงานนั้นได้ ทั้งที่สิทธิ์จริงอยู่ที่ RLS

**มาตรการ** — ใส่ข้อความกำกับในหน้าตั้งค่าสิทธิ์ว่าตารางนี้ควบคุมการแสดงเมนูเท่านั้น และให้หน้าจอแสดงข้อความผิดพลาดจากฐานข้อมูลตรง ๆ เมื่อการบันทึกถูกปฏิเสธ ไม่กลบเป็น "เกิดข้อผิดพลาด" ลอย ๆ

### 18. การออกจากระบบ — ต่ำ

ข้อกำหนดระบุถูกต้องแล้วว่าไม่ควรอ้างว่าออกจากบัญชี Google ทั้งเบราว์เซอร์

**มาตรการที่ต้องทำใน frontend** — เรียก `supabase.auth.signOut({ scope: 'local' })` ล้าง cache ของ TanStack Query ทั้งหมด (สำคัญ เพราะอาจมีข้อมูลผู้รับเงินค้างอยู่) และ redirect ไปหน้าเข้าสู่ระบบ ข้อความในป๊อปอัพควรบอกตรง ๆ ว่าออกจากระบบนี้เท่านั้น บัญชี Google ยังอยู่

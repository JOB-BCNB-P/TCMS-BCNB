## 1. ภาพรวมและข้อจำกัดที่กำหนดการออกแบบ

ระบบนี้จ่ายเงินงบประมาณแผ่นดินและถูกตรวจสอบโดยหน่วยตรวจสอบภายในและสำนักงานการตรวจเงินแผ่นดิน จึงมีข้อกำหนดที่ **ไม่ใช่** ข้อกำหนดของเว็บแอปทั่วไปสามข้อ ซึ่งเป็นตัวกำหนดรูปร่างของสถาปัตยกรรมทั้งหมด

| ข้อกำหนด | ผลต่อการออกแบบ |
|---|---|
| ตามรอยได้ว่าใครทำอะไรเมื่อใด | ตาราง `audit.activity_log` แบบเขียนอย่างเดียว ติด trigger ทุกตารางการเงิน และห้าม UPDATE/DELETE แม้โดยบทบาทผู้ดูแลระบบ |
| เอกสารที่จ่ายเงินแล้วต้องไม่เปลี่ยน | trigger ล็อกเอกสารสถานะ `paid` ทั้งหัวและบรรทัด แก้ไม่ได้ ลบไม่ได้ — ต้องทำเอกสารกลับรายการ |
| เบิกเกินวงเงินไม่ได้ | trigger `guard_budget_ceiling` ตรวจที่ฐานข้อมูล ไม่ใช่ที่หน้าจอ |

ข้อกำหนดข้อที่สี่มาจาก พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล: **เลขที่บัญชีธนาคาร** ของอาจารย์พิเศษและแหล่งฝึก เป็นข้อมูลที่รั่วแล้วเสียหายทันทีและกู้คืนไม่ได้ จึงถูกแยกออกจากฐานข้อมูลส่วนที่เปิดผ่าน API ทั้งหมด

**การ deploy** — **GitHub Pages** จาก repo สาธารณะ `JOB-BCNB-P/TCMS-BCNB`
เหมือนที่ระบบ AAMS ของวิทยาลัยใช้อยู่ deploy อัตโนมัติด้วย `.github/workflows/deploy.yml` ทุกครั้งที่ push ขึ้น `main`

เว็บอยู่ที่ `https://job-bcnb-p.github.io/TCMS-BCNB/` ซึ่งไม่ใช่รากของโดเมน จึงมีสามจุดที่ต้องตั้งให้ตรงกัน

| จุด | ค่า | ถ้าตั้งผิดจะเกิดอะไร |
|---|---|---|
| `vite.config.ts` → `base` | `/TCMS-BCNB/` | ไฟล์ JS/CSS ถูกอ้างจาก `/` แล้วโหลดไม่เจอ หน้าขาวทั้งหน้า |
| Router | `HashRouter` | GitHub Pages ไม่มี rewrite ผู้ใช้ที่กด refresh หรือเปิดลิงก์ลึกจะเจอ 404 ของ GitHub |
| Supabase → URL Configuration | `https://job-bcnb-p.github.io/TCMS-BCNB/` | ล็อกอิน Google แล้วเด้งกลับผิดที่ เข้าระบบไม่ได้ |

**ตัวแปรสภาพแวดล้อม** — ตั้งเป็น GitHub Secrets (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`)
เก็บใน Secrets เพื่อให้เปลี่ยนคีย์ได้โดยไม่ต้องแก้โค้ด **ไม่ใช่เพราะ anon key เป็นความลับ** — คีย์นี้ถูกฝังใน
JavaScript ที่ deploy ออกไปอยู่ดี และออกแบบมาให้เปิดเผยได้ ความปลอดภัยจริงอยู่ที่ RLS

`service_role` key **ห้ามอยู่ใน repo, ใน Secrets ของ workflow นี้ หรือที่ใดก็ตามที่แตะ frontend**
เพราะ key นี้ข้ามm RLS ได้ทั้งหมด workflow มีด่านตรวจรูปแบบคีย์ลับและจะหยุด deploy ถ้าเจอ

### 2.1 ผลของการเป็น repo สาธารณะ

วิทยาลัยเลือกให้ repo เป็นสาธารณะเพื่อใช้ GitHub Pages ฟรีเหมือน AAMS ซึ่งยอมรับได้ แต่ต่างจาก AAMS ตรงที่ระบบนี้คุมเลขบัญชีธนาคารและหลักฐานการเบิกจ่าย จึงมีสองข้อที่ต้องทำให้เป็นนิสัย

1. **ไฟล์ข้อมูลและเอกสารภายในห้ามอยู่ใน repo** — `.gitignore` กัน `*.pdf`, `*.csv`, `*.xlsx`, `TCMS-BCNB.md` และโฟลเดอร์ `_private/` ไว้แล้ว และ workflow ตรวจซ้ำอีกชั้นก่อน deploy ทุกครั้ง เพราะไฟล์ที่ commit ไปแล้วจะอยู่ในประวัติ git ตลอดไปแม้ลบภายหลัง
2. **RLS policy ทั้งชุดเปิดเผยต่อสาธารณะ** — ผู้ไม่หวังดีศึกษาหาช่องโหว่แบบออฟไลน์ได้ ซึ่งแปลว่าความถูกต้องของ policy ต้องพิสูจน์ได้ ไม่ใช่หวังว่าไม่มีใครเห็น — นี่คือเหตุผลที่ชุดทดสอบ 37 ข้อรันอัตโนมัติทุก pull request และต้องผ่านครบก่อน merge

## 3. การยืนยันตัวตนและบทบาท

### 3.1 สามด่านของการเข้าระบบ

1. **Google OAuth Client** — ตั้งเป็น Internal ใน Google Cloud ขององค์กร
2. **Trigger `enforce_bcn_domain` บน `auth.users`** — ปฏิเสธอีเมลที่ไม่ลงท้าย `@bcn.ac.th` ที่ชั้นฐานข้อมูล
   *เหตุผล:* Supabase ไม่บังคับ `hd` claim ของ Google Workspace ให้เอง ถ้าพึ่งการตั้งค่าฝั่ง Google อย่างเดียว บัญชี Gmail ทั่วไปอาจสมัครเข้ามาได้
3. **`user_profiles.is_active` ตั้งต้นเป็น `false`** — ผู้ใช้ใหม่ล็อกอินได้แต่ไม่เห็นข้อมูลใด ๆ จนกว่าผู้ดูแลระบบจะกำหนดบทบาทและเปิดใช้งาน

### 3.2 บทบาทและขอบเขต

| บทบาท | ขอบเขตข้อมูล | เขียนข้อมูลหลัก | เอกสาร | สถานะการเงิน | เลขบัญชี |
|---|---|---|---|---|---|
| ผู้ดูแลระบบ (`admin`) | ทุกสาขา | ✓ | ✓ ทั้งใบเบิกและหน้างบฯ | ✓ | ✓ |
| งานวิชาการ (`academic`) | ทุกสาขา | ✓ | ✓ ใบเบิก | ✗ | ✗ (เห็นจุดเขียว) |
| เลขานุการ (`secretary`) | เฉพาะสาขาที่ผูกไว้ | ✓ เฉพาะสาขาตน | ✓ ใบเบิก + เช็คลิสต์ | ✗ | ✗ |
| งานการเงิน (`finance`) | ทุกสาขา | ✗ | ✓ หน้างบฯ | ✓ | ✓ |
| อาจารย์ (`instructor`) | เฉพาะสาขาตน | ✗ | ✗ | ✗ | ✗ |
| ผู้บริหาร (`executive`) | ทุกสาขา | ✗ | ✗ | ✗ | ✗ |

เลขานุการสองคนตามข้อกำหนดทำได้โดยใส่แถวใน `user_department_scopes`:

- คนที่ 1 → `PED`, `MAT`, `PSY`
- คนที่ 2 → `ADU`, `COM`

### 3.3 จุดที่ต้องระวัง: `role_menu_permissions` ไม่ใช่ระบบความปลอดภัย

ข้อกำหนดระบุว่าผู้ดูแลระบบ "ปิด-เปิดสิทธิ์การเข้าถึงเมนูของแต่ละบทบาทได้" ตารางนี้ทำหน้าที่นั้น **แต่มันควบคุมได้แค่การซ่อนปุ่มบนหน้าจอ**
ผู้ที่เปิด DevTools แล้วยิง REST ตรงไปที่ Supabase จะไม่ผ่านตารางนี้เลย
สิทธิ์จริงทั้งหมดจึงอยู่ที่ RLS policy และ RPC ที่ฐานข้อมูล — และการติ๊กเปิดเมนูให้บทบาทหนึ่ง **จะไม่ทำให้บทบาทนั้นเขียนข้อมูลได้จริง** หากไม่ได้แก้ policy ควบคู่กันไปด้วย ข้อนี้ต้องสื่อสารกับผู้ดูแลระบบให้ชัด

### 3.4 ทำไมไม่เก็บบทบาทไว้ใน JWT

ทางเลือกหนึ่งคือใช้ custom access token hook ใส่บทบาทลง JWT เพื่อให้ RLS เร็วขึ้น แต่ JWT มีอายุ ~1 ชั่วโมง **ถ้าถอนสิทธิ์ผู้ใช้กลางคัน token เดิมจะยังทำงานได้จนหมดอายุ** สำหรับระบบการเงินความล่าช้านี้ยอมรับไม่ได้ ระบบจึงอ่านบทบาทจากตารางจริงผ่านฟังก์ชัน `STABLE` และเรียกใน policy ด้วยรูปแบบ `(select public.current_role_code())` ซึ่ง PostgreSQL จะประเมินเป็น InitPlan เพียงครั้งเดียวต่อ query ไม่ใช่รายแถว — ได้ความถูกต้องโดยไม่เสียประสิทธิภาพ

และไม่ว่ากรณีใด **ห้ามเก็บบทบาทใน `raw_user_meta_data`** เด็ดขาด เพราะผู้ใช้แก้ค่าตัวเองได้ผ่าน `supabase.auth.updateUser()` นี่เป็นช่องโหว่ที่พบบ่อยที่สุดในระบบที่สร้างบน Supabase

## 4. การจัดการเลขที่บัญชีธนาคาร

ตามที่เลือกไว้: แยกตาราง + RLS + audit

```
public.payees.has_bank_account  (boolean)   ← ทุกบทบาทเห็น = จุดสีเขียว
        ▲ trigger sync
private.bank_accounts                        ← ไม่อยู่ใน Exposed schemas
   owner_type | owner_id | bank_code | account_no | account_name
        ▲
        │ ทางเข้าเดียว
public.get_bank_account(owner_type, owner_id, purpose)   SECURITY DEFINER
public.upsert_bank_account(...)                          SECURITY DEFINER
        │
        └─► audit.sensitive_access_log  (ใครดู ของใคร เมื่อไหร่ เพื่ออะไร)
```

คุณสมบัติสำคัญ:

- `private` ไม่ถูกเพิ่มใน Data API → Exposed schemas ดังนั้น **ไม่มีทางยิง REST ถึงตารางนี้ได้เลย** ไม่ว่าจะเดา endpoint อย่างไร
- RPC บังคับให้ระบุ `purpose` อย่างน้อย 5 ตัวอักษร ทำให้ล็อกมีความหมายเวลาตรวจสอบ ไม่ใช่แค่ timestamp เปล่า
- `audit.sensitive_access_log` **ไม่เก็บเลขบัญชี** เก็บแค่ว่าใครเข้าถึงของใคร — ไม่งั้นล็อกจะกลายเป็นแหล่งรั่วแหล่งที่สอง
- คอลัมน์ `has_bank_account` ถูก `REVOKE UPDATE` จาก `authenticated` แล้ว client จึงปลอมจุดเขียวไม่ได้

**ความเสี่ยงที่ยังเหลืออยู่** — เลขบัญชียังเก็บเป็นข้อความธรรมดาในฐานข้อมูล ผู้ที่ถือ `service_role` key หรือเข้าถึง Dashboard ของ Supabase ได้ จะอ่านได้โดยไม่ผ่าน audit ทางแก้ระยะถัดไปคือเข้ารหัสด้วย Supabase Vault (pgsodium) แล้วให้ RPC เป็นผู้ถอดรหัส ซึ่งจะกันแม้แต่ผู้ที่ดึง backup ไปได้ — แนะนำให้ทำก่อนเปิดใช้งานจริงกับข้อมูลชุดเต็ม

### 5.1 `course_offerings` คือหน่วยตั้งงบและเบิกจ่าย

รายวิชาเดียวกันเปิดสอนคนละปีการศึกษา/ภาค/รุ่น มีวงเงินคนละก้อน จึงไม่ผูกงบกับ `courses` แต่ผูกกับ `course_offerings` ซึ่งถือ `academic_year_id`, `semester_id`, `fiscal_year_id`, `student_year_level`, `cohort_no`, `room`

`department_id` ถูกสำเนาลงมาใน `course_offerings` และ `payment_vouchers` เพื่อให้ RLS ตัดสินได้โดยไม่ต้อง join สองชั้นทุกแถว — ความถูกต้องดูแลโดย trigger `sync_offering_keys` และ `sync_voucher_keys` ไม่ใช่ความหวังดีของฝั่ง frontend

### 5.2 การจัดการวันที่

- **วันที่ปฏิทิน** (วันที่จ่ายเงิน วันที่รับเงิน วันที่เอกสาร) → `date` เก็บเป็น ค.ศ. มาตรฐาน
- **เวลาประทับเหตุการณ์** (สร้าง แก้ไข อนุมัติ) → `timestamptz` เก็บ UTC
- **แปลงเป็น พ.ศ. ที่ชั้น UI เท่านั้น** ไม่เก็บ พ.ศ. ลงคอลัมน์วันที่เด็ดขาด เพราะจะคำนวณช่วงเวลาผิดทั้งระบบ
- ปีการศึกษาและปีงบประมาณเก็บเป็น `smallint` พ.ศ. ได้ เพราะเป็น "ชื่อปี" ไม่ใช่ "วันที่"
- `public.fiscal_year_be(date)` คืนปีงบประมาณ โดยเดือน ต.ค. ขึ้นไปนับเป็นปีถัดไป

### 5.3 สถานะการเบิกจ่าย

```
draft ──submit──► submitted ──verify──► verified ──pay──► paid   (สิ้นสุด)
  ▲                   │                     │
  └──(admin ย้อน)─────┘                     └──(admin ย้อน)──► submitted
                              cancelled ◄── (admin, ต้องระบุเหตุผล, ห้ามหลังจ่ายแล้ว)
```

หน้าจอแสดง "อยู่ระหว่างดำเนินการ" สำหรับทุกสถานะที่ยังไม่ใช่ `paid` ตามที่ข้อกำหนดระบุ

การเปลี่ยนสถานะทั้งหมดผ่าน RPC `public.set_voucher_status()` ทางเดียว **เจ้าหน้าที่การเงินไม่ได้รับสิทธิ์ `UPDATE` บน `payment_vouchers` เลย** เพราะ RLS ทำงานระดับแถว ไม่ใช่ระดับคอลัมน์ — ถ้าให้สิทธิ์ UPDATE เพื่อให้แก้สถานะได้ ก็จะแก้ยอดเงินได้ด้วย ซึ่งยอมรับไม่ได้ในระบบการเงิน

RPC ยังบังคับกฎเชิงกระบวนงานก่อนส่งเอกสาร ได้แก่ ต้องมีรายการอย่างน้อยหนึ่งบรรทัด และเช็คลิสต์เอกสารแนบ 7 ข้อต้องติ๊กครบ

**วิธีที่แนะนำ: พิมพ์ผ่านเบราว์เซอร์**
สร้าง HTML ที่จำลองแบบฟอร์มด้วย CSS `@page { size: A4 landscape }` แล้วใช้ `window.print()` ให้ผู้ใช้เลือก "Save as PDF"

เหตุผลที่ไม่ใช้ jsPDF หรือ pdfmake: ไลบรารีเหล่านี้รองรับการเรียงพยัญชนะ สระ และวรรณยุกต์ภาษาไทยได้ไม่ดี สระบนและวรรณยุกต์มักซ้อนผิดตำแหน่งหรือหาย ซึ่งใช้ไม่ได้กับเอกสารที่ต้องส่งฎีกา ส่วนเบราว์เซอร์ใช้ HarfBuzz จัดวางให้ถูกต้องอยู่แล้ว

ถ้าต้องการไฟล์ PDF อัตโนมัติโดยผู้ใช้ไม่ต้องกด (เช่น แนบอีเมล) ให้ทำเป็น Supabase Edge Function ที่เรียก Puppeteer เรนเดอร์หน้าเดียวกัน — ใช้เอนจินเดียวกันจึงได้ผลลัพธ์ตรงกัน

**ข้อควรระวัง:** ฟอนต์ Sarabun ต้อง self-host ใน repo ไม่ดึงจาก Google Fonts CDN เพราะเครื่องในวิทยาลัยบางส่วนอาจถูกจำกัดการออกอินเทอร์เน็ต และเอกสารที่พิมพ์ต้องได้ผลเหมือนกันทุกเครื่อง

## 7. การนำเข้าไฟล์ CSV

ทุกเมนูต้องรองรับ upload CSV และดาวน์โหลดฟอร์มเปล่า แนวทาง:

1. อ่านและตรวจไฟล์ฝั่ง client ด้วย PapaParse + schema ของ Zod ต่อหนึ่งเมนู
2. แสดงตารางพรีวิวพร้อมทำเครื่องหมายแถวที่ผิดก่อนยืนยัน
3. เมื่อยืนยัน จึง `insert` เข้า Supabase ตามปกติ — RLS และ trigger ทุกตัวยังทำงานเต็มที่ ไม่มีทางลัด
4. จำกัดขนาดไฟล์และจำนวนแถวต่อครั้ง (แนะนำ 2 MB / 1,000 แถว) และแบ่ง insert เป็นก้อนละ 200 แถว

**ตอน export CSV ต้องกัน CSV injection** — ค่าใดที่ขึ้นต้นด้วย `=`, `+`, `-`, `@`, tab หรือ CR ให้ใส่ `'` นำหน้า มิฉะนั้นเปิดใน Excel แล้วสูตรจะทำงาน ซึ่งเป็นช่องทางโจมตีเครื่องเจ้าหน้าที่การเงิน

## 8. หน้าแดชบอร์ด

ข้อมูลทั้งหมดมาจากสอง view ที่ประกาศ `security_invoker = true` (RLS ของตารางต้นทางมีผลกับผู้เรียก):

- `public.v_budget_usage` — วงเงินที่จัดสรร / ใช้ไปแล้ว / คงเหลือ ต่อรายวิชา × หมวดเงิน
  ใช้กับกราฟเส้นการใช้งบประมาณ ตารางเงินที่ใช้ไปแล้ว และตารางเงินคงเหลือ
- `public.v_payment_summary` — ตารางสรุปการจ่ายเงินรายบรรทัด (คำนำหน้า–ชื่อ–สกุล ผู้สอน, รายวิชา, เดือน, ปี พ.ศ., รายการ, ชั้นปี, จำนวนเงิน, วันที่จ่าย, ธนาคาร)
  **ไม่มีคอลัมน์เลขบัญชีโดยเจตนา**

การแบ่งหน้า 10 แถวพร้อมปุ่ม ถัดไป/ก่อนหน้า/สุดท้าย ใช้ `.range(from, to)` ของ Supabase client คู่กับ `count: 'exact'` ไม่ดึงทั้งตารางมาแบ่งหน้าที่ฝั่ง client

## 9. ลำดับการติดตั้ง

```bash
supabase link --project-ref iyznviulnxmiffezvrdh
supabase db push          # รัน migration 0001-0006 ตามลำดับ
```

จากนั้นใน Supabase Dashboard:

1. **Authentication → Providers → Google** เปิดใช้งาน ใส่ Client ID/Secret ของ OAuth client แบบ Internal
2. **Authentication → URL Configuration** ใส่ Site URL และ Redirect URLs ของโดเมนจริงเท่านั้น
3. **Project Settings → Data API → Exposed schemas** ตรวจให้แน่ใจว่ามีเพียง `public` และ `graphql_public` — **ห้ามมี `private` หรือ `audit`**
4. **Authentication → Sessions** ลดอายุ JWT เหลือ 30 นาที และเปิด refresh token rotation
5. เข้าสู่ระบบด้วยบัญชีผู้ดูแลระบบครั้งแรก แล้วรัน SQL ครั้งเดียวเพื่อยกสิทธิ์ตัวเอง:

```sql
update public.user_profiles
   set role_id = (select id from public.roles where code = 'admin'),
       is_active = true, activated_at = now()
 where email = 'oranit.r@bcn.ac.th';
```

หลังจากนั้นผู้ใช้อื่นทั้งหมดเปิดสิทธิ์ผ่านหน้าจัดการผู้ใช้งาน (RPC `admin_set_user_role`)
